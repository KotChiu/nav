# MotoNav 开发路线图

更新时间：2026-11-09；主要工作分支：`feature/board-2.1`。

本路线图区分 **源码存在**、**构建/烧录验证** 与 **实车可用**。没有完整的设备/道路测试证据时，不能标成“已交付”。

## P0 — 先补稳定性与验证门槛

- [ ] **刷屏容错**：为 `flushWait()` 的超时提供真实降级/恢复路径；检查刷屏任务、信号量、PSRAM 分配失败并添加故障注入测试。
- [ ] **2.1 实机状态回归**：0°/90°/180°/270°/314° 的导航、页面、滑动、触摸坐标、来电与音乐测试；记录闪屏、撕裂、丢帧及内存峰值。
- [ ] **BLE 回归**：新/旧 Android 与 iOS 的配对、断连恢复、地图分片 ACK、封面、文字位图、音乐/HID、消息中断与导航到达准出。
- [ ] **电池硬件核实**：先查 2.1 实板供电测量能力，再决定 USB/充电检测或明确“未知”状态；不要凭空实现 AXP2101。

**准出标准**：固定测试板型、固件 SHA、手机 App 版本、场景与可复现的测试记录；阻塞 UI/导航的故障已消除，不能只凭单次串口启动日志放行。

## P1 — 有基线的显示性能改进

- [ ] 建立独立测量：`touch IRQ → 采样 → 状态变更 → LVGL/Canvas → flush → 可见画面`，按角度/页面统计 p50/p95/max，采集内存、BLE 队列与屏幕撕裂。
- [ ] 评估 0° 路径的脏区域/双缓冲复制策略；确认局部刷新正确性和生命周期后再减少整帧复制。
- [ ] 任意角度旋转只在可证明正确的区域做局部更新，验证边框、触摸映射与切页快照不残影。
- [ ] 用相同设备/画面/角度做 A/B：比较耗时分布、峰值内存、稳定性；任何视觉收益不能牺牲导航数据及时性。

现有 [性能记录](UI-PERFORMANCE-2026-11-08.md) 是阶段计时，不是端到端 FPS 或触摸响应结论。

## P1 — 手机与 BLE 数据新鲜度

- [ ] iOS 股票请求增加“请求代际 ID + 周期/自选列表快照”检查，避免取消/过期任务回调覆盖当前 K 线。
- [ ] 行情和 K 线采用差量/节流发送：自选列表没变化时不要重复传名称位图和全部历史数据。
- [ ] 完善 BLE 队列背压、地图/封面优先级和网络超时后的降级文案；优先保证导航数据与控制指令。
- [ ] 把手机/固件协议契约变成可运行的兼容测试，覆盖乱序、重复、断包、重连和旧版忽略新消息。

## P2 — 工程化与维护

- [ ] 在 CI 加入现有 C++ 协议/策略测试、Python 烧录脚本测试、Android Gradle/纯逻辑测试及 iOS 具备 macOS 环境的静态/构建检查。
- [ ] 逐步拆分高耦合代码：Android `MainActivity.kt`、固件 `LvglOverlay.h` 等；保持接口、编译单元和生命周期不变。
- [ ] 梳理 1.75 与 2.1 可以共享的协议和纯逻辑代码；驱动/电源/面板仍保留板型边界。
- [ ] 定义版本/源码/发布资产的检查清单，避免 README 声称已提供未发布的新版包。

## 建议的第一轮任务（按顺序）

1. **可靠性 PR**：`flushWait()` 超时与资源创建失败处理 + 构造故障的回归测试。
2. **性能基线 PR**：不动像素算法，先补阶段/端到端埋点和采集说明。
3. **股票数据 PR**：请求代际隔离、缓存/差量发送，降低 BLE 额外负担。
4. **显示优化 PR**：在已测瓶颈上做小范围改动，所有角度/页面实机回归。

代码依据与复现方式见 [2026-11-09 代码审查](CODE-REVIEW-2026-11-09.md)。所有任务未勾选前不代表已经开发或验证。
