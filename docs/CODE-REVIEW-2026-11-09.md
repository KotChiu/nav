# MotoNav 代码优化审查 · 2026-11-09

**审查范围**：`KotChiu/nav` 的 `feature/board-2.1` 默认分支，以 2.1 ESP32 固件渲染/任务/供电、BLE 和 iOS 股票链路为重点，同时检查 Android/iOS 的目录边界与现有测试入口。**方法为 GitHub 源码静态审查**，本次**未本地编译、未运行测试、未连接实物采样**。以下的“风险”不等于已复现故障；实施前需通过构造场景复核。

## 按优先级排序

### 高优先级 1：刷屏超时后退化为永久等待

- **证据**：[`DisplayPipeline.h` L183–186](../firmware/boards/21/MotoNav/src/display/DisplayPipeline.h#L183-L186) — `flushWait()` 先等 3000ms，失败后又执行 `portMAX_DELAY` 无限等待。后续 `flushAsync/flushSync` 会依赖此等待。
- **影响**：如果刷屏任务停止、VSYNC 不再推进或 `flushDone` 丢失，主循环可能无法继续更新导航与触摸。**异常分支具有确定的无限等待行为**；实际触发概率未知。
- **建议**：明确区分“正常等待”和“超时恢复”：记录异常计数、保持缓冲所有权安全、有限次恢复或切换受控故障画面；不要在未验证缓冲一致性时直接放行绘制。
- **验收**：人工注入刷屏任务不响应 / VSYNC 停滞，主循环能进入可诊断的降级状态，既不永久等待也不写入已被刷屏任务占用的缓冲。

### 高优先级 2：双缓冲初始化资源/任务失败未完整处理

- **证据**：[`DisplayPipeline.h` L213–231](../firmware/boards/21/MotoNav/src/display/DisplayPipeline.h#L213-L231) — 申请第二缓冲失败会返回，但信号量创建后没有逐项检查，`xTaskCreatePinnedToCore` 返回值也未用于判断是否真的有刷屏任务。
- **影响**：PSRAM 紧张或任务创建失败时，可能进入不可恢复的等待；部分失败路径未明确清理或降级。
- **建议**：集中 `DisplayResources` 初始化，检查 PSRAM、两个 semaphore、任务结果；失败时仅采用有完整边界的同步渲染回退，或者明确停止启动且输出可观测故障信息。
- **验收**：PSRAM/任务/信号量三类故障注入均有可预测行为，且不会将未创建的 task 当作已启动。

### 高优先级 3：iOS 股票 K 线存在过期异步响应覆盖风险

- **证据**：[`StockBridge.swift` L160–168](../ios/MotoNav/StockBridge.swift#L160-L168) 切换周期会 cancel 旧任务并清空 candles；但 [L183–205](../ios/MotoNav/StockBridge.swift#L183-L205) 和 [L217–241](../ios/MotoNav/StockBridge.swift#L217-L241) 的完成回调仅验证股票仍在自选列表，并未验证结果所属周期 / 请求代际；`sendCandles()` 使用**当前** `period.protocolCode`。
- **影响**：已被取消但完成回调仍执行时，旧周期的 K 线可能进入新周期数据区并标记为新周期，造成图形与用户选择不一致。它是**由代码推导的竞态风险**，尚未实测。
- **建议**：为每轮 K 线请求附 `generation`、请求周期、列表快照及 task identity；仅在这几者仍匹配时提交结果。用受控的乱序回调测试覆盖“日 K→分钟 K→日 K”、删除股票及重连。
- **验收**：任何晚到/取消的旧请求都不会更新新周期的 candles 或下发 BLE。

### 中优先级 4：显示全帧复制和旋转仍是主要性能候选

- **证据**：[`DisplayPipeline.h` L93–148](../firmware/boards/21/MotoNav/src/display/DisplayPipeline.h#L93-L148) 的 0° 路径支持矩形 memcpy，但其他角度重新处理整帧；[L188–198](../firmware/boards/21/MotoNav/src/display/DisplayPipeline.h#L188-L198) 在 LVGL UI + 异步刷屏条件下还会复制整个 466×466 源缓冲并强制全帧。
- **代价**：466×466 RGB565 每个画布约 **424 KiB**；480×480 面板帧约 **450 KiB**。这些路径可能消耗内存带宽，具体瓶颈需结合调用频率和角度实测；不能凭 memcpy 存在就判定所有页面都慢。
- **建议**：先测当前真实的 `flushCopyUs`、VSYNC、页面准备与可见输出，再优化真正高频路径。优先检查 0° 的完整快照是否必要；任意角度做逆映射局部刷新需正确计算源/目标脏区、旋转边界和旧像素清理。
- **已知基线**：[2026-11-08 UI 性能记录](UI-PERFORMANCE-2026-11-08.md) 显示不同场景有约 25–58ms 的部分阶段计时，但**不等于固定 FPS 或端到端触摸延迟**。
- **验收**：固定板子/固件/角度/页面，对比 p50/p95 处理耗时、撕裂、视觉残影和内存峰值，不能只看单帧最低值。

### 中优先级 5：行情更新触发重复传输，容易与导航抢 BLE 带宽

- **证据**：[`StockBridge.swift` L64–68](../ios/MotoNav/StockBridge.swift#L64-L68) 每 60 秒刷新；[L98–109](../ios/MotoNav/StockBridge.swift#L98-L109) 成功后 `sendLatest()`、`fetchCandles()`；[L144–157](../ios/MotoNav/StockBridge.swift#L144-L157) 又为每只股票发送名称位图与 K 线数据，即使名称和 K 线未变。
- **影响**：最多八只股票可产生多次 HTTP 与 BLE 指令/位图，带宽开销与页面显示价值不一定相称；实际与导航的竞争程度尚未测量。
- **建议**：报价与图表按变更版本发送；名称位图缓存、在 BLE 重连时按需补发；行情页不在可见状态时降低频率；图表请求并发和队列优先级应不影响导航指令。
- **验收**：对照同一行情和相同连接条件，统计每分钟 BLE 字节/包、图表更新及时性、导航消息 p95 排队时间。

### 中优先级 6：2.1 电量 UI 将未知 USB/充电状态写为“未充电”

- **证据**：[`BatteryPolling.h` L11–23](../firmware/boards/21/MotoNav/src/power/BatteryPolling.h#L11-L23) 将 `chg` / `usb` 固定设为 `false` 并上报；[`Battery.h`](../firmware/boards/21/MotoNav/src/power/Battery.h) 则明确说明没有已确认的供电状态寄存器、自动关机策略应保守处理未知供电。
- **影响**：设备可能正在外接电源，但 App 协议里显示“未充电/无 USB”。**这不等于设备目前会因插电误关机**，现有策略意在避免该错误。
- **建议**：有可靠硬件信号时实现真实检测；否则协议与 UI 明确区分“未知”和“否”，并在低电、插拔电及无电池三种状态下验证。
- **验收**：USB/充电显示不再将未知当作否；未知状态不影响现有保守自动关机安全策略。

### 维护性 7：大文件与跨板重复代码增加 AI Coding 误改概率

- **证据**：Android `MainActivity.kt` 文件体量大；2.1 `src/display/LvglOverlay.h` 混合了 LVGL 控件创建、股票、音乐、触摸和局部失效状态；1.75 / 2.1 各有固件实现树。
- **风险**：引入 UI 改动容易触及显示生命周期、全局状态和多个平台版本；直接大规模重构会放大回归风险。
- **建议**：优先抽共享的纯逻辑/协议（报文解析、校验、缓存策略），不要贸然统一 1.75 和 2.1 的面板驱动；逐个功能提取边界和单元测试。
- **验收**：每一步保持功能/协议兼容，且编译/单测/实机对照结果与原版一致。

## 建议优先实施的测试

| 场景 | 应记录的指标 / 期望 |
| --- | --- |
| 刷屏线程卡住、VSYNC 中断、内存申请失败 | 有限时间恢复/报错，主循环无永久死锁，缓冲不被并发破坏 |
| 0°、90°、180°、270°、314° 滑动与导航 | 阶段时延与端到端 p50/p95、错误像素/撕裂/残影、堆剩余 |
| BLE 大包乱序、重复、断连/重连 | ACK、数据有效性及版本匹配；高优先级导航指令延迟 |
| 股票日 K/分钟 K 快速切换、移除、重连 | 旧请求不覆盖新周期，BLE 传输不会重复淹没队列 |
| USB 插拔、无电池、低电量 | 显示“未知/未充电/充电中”语义正确，自动关机策略不回退 |

**建议优先顺序**：先修刷屏等待与初始化容错 → 修 iOS 股票异步竞态 → 建立统一测量 → 再尝试局部刷新和差量传输。不要先做没有同场景实测的“FPS 大改”。

## 验证边界与变更记录

本审查未直接改动固件和手机端业务代码，也未执行构建与测试。现有 [UI 现场测量记录](UI-PERFORMANCE-2026-11-08.md) 来自仓库先前记录，本次仅引用其既有结论，不视为本轮重新验证。后续每条优化建议应独立建任务、附测试证据、留回滚点。
